# Speculative decoding

Speculative decoding reduces inter-token latency by generating multiple *draft*
tokens cheaply and then verifying them in a single parallel forward pass of the
target model. When the target model accepts a draft token, you get that token
for free — no extra forward pass required. Rejected tokens are discarded and
regenerated by the target model, so the output distribution is preserved
exactly.

For a formal treatment see
[Accelerating Large Language Model Decoding with Speculative Sampling](https://arxiv.org/pdf/2302.01318).

To train your own draft models for optimized speculative decoding, see
[vllm-project/speculators](speculators.md).

---

## How speculative decoding works

Each decoding step has two phases:

1. **Draft phase** — a lightweight *proposer* generates `N` candidate tokens
   quickly. The proposer can be a small neural network, a lookup table, or a
   pattern-matching algorithm.
2. **Verification phase** — the full target model evaluates all `N` draft
   tokens in a single batched forward pass. Tokens are accepted or rejected
   using a rejection-sampling scheme that preserves the target distribution.

The net result is that accepted tokens cost almost nothing beyond the
verification pass, so throughput and latency both improve when the acceptance
rate is high.

```
Prompt tokens ──► [Draft proposer] ──► draft_1, draft_2, …, draft_N
                                                │
                        ┌───────────────────────┘
                        ▼
              [Target model — single forward pass]
                        │
                        ▼
              Accept / reject each draft token
                        │
                        ▼
              Emit accepted tokens + one bonus token
```

## Available methods

vLLM supports a variety of speculative decoding methods. Model-based methods
such as EAGLE, MTP, draft models, PARD, and MLP provide the best latency
reduction. Simpler methods such as n-gram and suffix decoding provide modest
speedups without increasing workload during peak traffic.

| Method | Guide | Proposer type | Extra model required |
|---|---|---|---|
| **EAGLE / EAGLE3** | [eagle.md](eagle.md) | Neural network (single transformer layer) | Yes — EAGLE head |
| **MTP** | [mtp.md](mtp.md) | Neural network (built into target model) | No |
| **Draft model** | [draft_model.md](draft_model.md) | Full smaller LLM | Yes — separate model |
| **Parallel draft model (PARD)** | [parallel_draft_model.md](parallel_draft_model.md) | Full smaller LLM, parallel | Yes — PARD model |
| **MLP speculator** | [mlp.md](mlp.md) | MLP conditioned on hidden states | Yes — MLP head |
| **N-gram** | [n_gram.md](n_gram.md) | Prompt lookup (CPU or GPU) | No |
| **Suffix decoding** | [suffix.md](suffix.md) | Suffix-tree lookup | No |
| **Medusa** | [medusa.md](medusa.md) | Multiple parallel MLP heads | Yes — Medusa heads |

## Algorithm comparison

### EAGLE

EAGLE (Extrapolation Algorithm for Greater Language-model Efficiency) trains a
lightweight auto-regressive draft model that takes the target model's hidden
states as additional input. Because it conditions on the target's internal
representations, it achieves high acceptance rates with only one or two
transformer layers.

EAGLE3 extends EAGLE by using auxiliary hidden states from multiple layers of
the target model, further improving acceptance rates for large models.

**Best for:** General-purpose latency reduction. Strong acceptance rates across
diverse tasks.

### MTP (multi-token prediction)

MTP uses prediction heads that are built directly into the target model. No
separate draft model is needed. The target model predicts multiple tokens per
forward pass during training, and those extra heads are reused at inference
time.

**Best for:** Models that natively support MTP (e.g., DeepSeek, MiMo, Qwen3).

### Draft model

A separate, smaller LLM generates draft tokens autoregressively. The draft
model shares the same vocabulary as the target model but has fewer parameters.

**Best for:** Situations where a well-matched smaller model exists and you want
maximum flexibility in draft quality vs. speed.

### Parallel draft model (PARD)

PARD generates all speculative tokens in a single parallel forward pass of the
draft model rather than autoregressively. This reduces draft latency
significantly at the cost of slightly lower acceptance rates compared to
sequential drafting.

**Best for:** High-throughput scenarios where draft latency is a bottleneck.

### MLP speculator

An MLP conditioned on the target model's hidden states and the previously
sampled token predicts the next several tokens. IBM Research's MLP speculator
is a well-known example.

**Best for:** Workloads where a compatible MLP speculator is available and you
want a lightweight alternative to a full draft model.

### N-gram (prompt lookup decoding)

N-gram speculation searches the current context for the longest suffix that
matches a prefix elsewhere in the prompt or generated text, then proposes the
tokens that follow that match. No neural network is involved.

vLLM provides two implementations:

- **CPU (`ngram`)** — uses Numba-JIT compiled code for fast CPU-side lookup.
- **GPU (`ngram_gpu`)** — fully vectorized PyTorch operations on GPU, compiled
  with `torch.compile` for async execution.

**Best for:** Tasks with high repetition in the prompt (e.g., document
summarization, code completion with boilerplate, RAG with long contexts).

### Suffix decoding

Suffix decoding builds a global suffix tree over all past responses and a
per-prompt suffix tree. It proposes the most likely continuation based on
frequency counts and adapts the speculation depth dynamically per request.

**Best for:** Tasks with high repetition across requests (e.g., code editing,
agentic loops, RL rollouts).

### Medusa

Medusa adds multiple independent MLP heads to the target model, each predicting
a different future token position. All heads run in parallel during the target
model's forward pass, so draft generation adds minimal overhead.

**Best for:** Situations where Medusa heads have been trained for your specific
target model.

## Method selection at a glance

Use this table as a starting point. Real gains depend on your model family,
traffic pattern, hardware, and sampling settings.

| Method | Low QPS (latency) | High QPS (throughput) | Notes |
|---|---|---|---|
| EAGLE / EAGLE3 | High gain | Medium–high gain | Strong general-purpose model-based method. |
| MTP | High gain | Medium–high gain | Best when the target model has native MTP support. |
| Draft model | High gain | Medium gain | Needs a separate draft model. |
| Parallel draft model (PARD) | High gain | Medium–high gain | Low draft model latency. |
| MLP speculator | Medium–high gain | Medium gain | Good when compatible MLP speculators are available. |
| N-gram | Low–medium gain | Medium gain | Lightweight and easy to enable. |
| Suffix decoding | Low–medium gain | Medium gain | No extra draft model; dynamic speculation depth. |
| Medusa | Medium–high gain | Medium gain | Requires Medusa heads trained for your model. |

For reproducible measurements in your environment, use
[`examples/offline_inference/spec_decode.py`](../../../examples/offline_inference/spec_decode.py)
or the [benchmark CLI guide](../../benchmarking/cli.md).

## Lossless guarantees

vLLM's speculative decoding is designed to be lossless with respect to the
target model's output distribution. This section breaks down the guarantees
into three areas.

### Theoretical losslessness

Speculative decoding sampling is theoretically lossless up to the precision
limits of hardware numerics. Floating-point errors may cause slight variations
in output distributions, as discussed in
[Accelerating Large Language Model Decoding with Speculative Sampling](https://arxiv.org/pdf/2302.01318).

### Algorithmic losslessness

vLLM's implementation is algorithmically validated to be lossless. Key
validation tests include:

- **Rejection sampler convergence** — ensures that samples from vLLM's
  rejection sampler align with the target distribution.
  [View test code](https://github.com/vllm-project/vllm/blob/47b65a550866c7ffbd076ecb74106714838ce7da/tests/samplers/test_rejection_sampler.py#L252)
- **Greedy sampling equality** — confirms that greedy sampling with speculative
  decoding matches greedy sampling without it. Almost all tests in
  [`tests/v1/spec_decode`](https://github.com/vllm-project/vllm/tree/main/tests/v1/spec_decode)
  verify this property.

### vLLM logprob stability

vLLM does not currently guarantee stable token log probabilities (logprobs).
This can result in different outputs for the same request across runs. For more
details, see the FAQ section *Can the output of a prompt vary across runs in
vLLM?* in the [FAQs](../../usage/faq.md).

### Sources of variation

Variations in generated outputs with and without speculative decoding can occur
due to:

- **Floating-point precision** — differences in hardware numerical precision
  may lead to slight discrepancies in the output distribution.
- **Batch size and numerical stability** — changes in batch size may cause
  variations in logprobs and output probabilities, potentially due to
  non-deterministic behavior in batched operations or numerical instability.

## Known feature incompatibilities

1. Pipeline parallelism is not composable with speculative decoding as of
   `vllm<=0.15.0`.
2. Speculative decoding with draft models is not supported in `vllm<=0.10.0`.
3. Multimodal models are not supported with draft models or parallel drafting.
4. M-RoPE (multi-dimensional rotary position embedding) is not supported with
   draft models or parallel drafting.
